# Power Dashboard

Збір телеметрії Marstek Venus E 3.0 (`VNSE3-0`, EMS 150) через Bluetooth Low Energy. Воркер використовує `dbus-next` і BlueZ на Ubuntu, а на macOS — `@stoprocent/noble` і CoreBluetooth. PostgreSQL зберігає історію для кожної станції. Next.js надає останній вимір через HTTP API.

Той самий воркер щохвилини збирає графіки відключень усіх черг ДТЕК Київської області з alerts.energy. Дашборд показує останні показники станції, поточні графіки та історію їхніх змін.

## Локальний запуск із VS Code

### Перегляд UI на моках

Встанови Node.js 24 і виконай `npm ci`. У **Run and Debug** вибери **Web Mock**, натисни **F5** і відкрий [http://127.0.0.1:3001](http://127.0.0.1:3001). З термінала той самий режим запускає `npm run dev:mock`.

Команда вмикає `DASHBOARD_MOCK=1` для локального режиму розробки. Дашборд відкривається без входу та показує демодані станції, графік відключень та історію. Для перегляду не потрібні `.env`, PostgreSQL, BLE або воркер.

### Запуск з реальною телеметрією

1. Встанови Node.js 24 і запусти `npm ci`. У `.env` заповни `PG*` за зразком у `.env.example`, дані станції та облікові дані дашборда. Для локального HTTP встанови `DASHBOARD_SECURE_COOKIE=false`.
2. Запусти PostgreSQL окремо:

   ```sh
   docker compose -f compose.db.yaml up -d --wait
   ```

   `compose.db.yaml` запускає лише PostgreSQL. Він доступний на `127.0.0.1` і використовує окремий том для локальної розробки. Якщо PostgreSQL уже працює локально, можна вказати його параметри в `PG*`.

3. У **Run and Debug** вибери **Power Dashboard** і натисни **F5**. VS Code застосує міграції, зареєструє станцію та запустить вебзастосунок і воркер. Відкрий адресу з термінала Next.js, типово `http://localhost:3000`.

Воркер сам визначає ОС. За потреби явно задай `BLE_HOST_OS=macos` або `BLE_HOST_OS=linux` відповідно до хоста. На Mac дозволь Bluetooth у **System Settings → Privacy & Security → Bluetooth**, якщо система запитає дозвіл. Воркер шукає Venus E 3.0 у радіусі дії та звіряє `STATION_DEVICE_ID` перед збереженням вимірів.

## Запуск на Ubuntu Server

1. Перевір, що служба Bluetooth активна, потрібний адаптер увімкнений і Ubuntu бачить MAC станції під час сканування.

   ```sh
   systemctl is-active bluetooth
   bluetoothctl list
   bluetoothctl --timeout 15 scan on
   bluetoothctl devices
   test -S /run/dbus/system_bus_socket
   ```

2. Скопіюй `.env.example` у `.env` і заповни його. Для Compose потрібні `POSTGRES_PASSWORD`, `API_USERNAME` і `API_PASSWORD`. Логін Basic Auth має бути без двокрапки. Задай усі п’ять полів станції, щоб увімкнути її збір.

   | Змінна | Значення |
   | --- | --- |
   | `STATION_ID` | Внутрішній текстовий ID станції для дашборда й API, наприклад `marstek-home` |
   | `STATION_NAME` | Назва станції, наприклад `Marstek Home` |
   | `STATION_MODEL` | `VNSE3-0` |
   | `STATION_DEVICE_ID` | Device ID з Marstek, з усіма цифрами |
   | `STATION_BLE_MAC` | BLE-адреса у форматі `02:00:00:00:00:01` |
   | `BLE_ADAPTER` | Адаптер BlueZ, типово `hci0` |
   | `POLL_INTERVAL_MS` | Інтервал опитування, типово `1000` |
   | `STALE_AFTER_MS` | Вік застарілого виміру, типово `5000` |
   | `API_PORT` | Порт API на `127.0.0.1`, типово `3000` |
   | `DASHBOARD_SESSION_SECRET` | Окремий серверний секрет для входу в дашборд. Згенеруй через `openssl rand -hex 32` |
   | `DASHBOARD_SECURE_COOKIE` | У Compose типово `true` для HTTPS. Для локальної перевірки через HTTP встанови `false` |

   Локальні процеси `npm run bootstrap`, `npm run worker` і API приймають змінні PostgreSQL `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`. Для воркера поза Compose типовий шлях системної шини визначає `dbus-next`. Його можна задати через `DBUS_SYSTEM_BUS_ADDRESS`.

3. Запусти застосунок. Сервіс `bootstrap` застосовує міграції та реєструє станцію перед запуском API й воркера. Повторний запуск зберігає всі виміри. Воркер читає список активних станцій під час старту, тому після додавання станції або зміни цього списку його треба перезапустити.

   ```sh
   docker compose up -d --build
   docker compose logs -f worker
   ```

   Для перевірки без BLE виконай `docker compose up -d --build api` і відкрий `http://127.0.0.1:3000`. Сокет системної шини D-Bus монтується лише у воркер. Оскільки профіль `docker-default` на Ubuntu може блокувати реєстрацію на шині, Compose задає `apparmor=unconfined` лише для `worker`. Після заміни сокета D-Bus на хості перествори контейнер воркера.

## Логи

Вебсервер, API, міграції та воркери пишуть по одному JSON-об’єкту на рядок. Кожен запис має `timestamp` у форматі ISO 8601 (UTC), `level` (`info`, `warn` або `error`), `component` і `message`. HTTP-записи містять метод, шлях без параметрів запиту, статус і тривалість.

```sh
docker compose logs -f api worker
```

При збої Marstek воркер записує `stationId`, етап `stage` і затримку до наступної спроби `retryInMs`. `ble.connect` охоплює підключення та перевірку пристрою, `ble.read` — запит телеметрії, а `database.save` — запис виміру. Рядок `First BLE measurement processed` підтверджує, що після підключення воркер отримав перший вимір і завершив запис у PostgreSQL.

## Дашборд

Відкрий `/` і ввійди з `API_USERNAME` та `API_PASSWORD`. Для входу потрібно задати `DASHBOARD_SESSION_SECRET`. Сеанс діє 8 годин. Зміна логіна, пароля або секрету завершує чинні сеанси після перезапуску сервісу. Для доступу поза локальним хостом використовуй HTTPS.

Дашборд отримує телеметрію і поточні графіки через WebSocket на `/ws/dashboard`. Вебпроцес використовує одне підключення PostgreSQL з `LISTEN` для всіх вкладок. Після початкового завантаження нові виміри й час останнього опитування джерела надходять через `NOTIFY`. Якщо набір версій графіка змінився, вебпроцес зчитує його один раз для всіх вкладок. Після розриву з’єднання дашборд автоматично підключається знову й показує останні отримані дані, поки чекає на нові.

Локально застосуй міграції через `npm run bootstrap`, потім запускай вебсервер через `npm run dev` або `npm run start` після збірки. Після змін у серверній частині WebSocket перезапусти вебпроцес. У Compose міграції застосовує сервіс `bootstrap`. Якщо використовуєш reverse proxy, передавай оригінальний `Host` і дозволь WebSocket Upgrade для `/ws/dashboard`. Для HTTPS браузер використовує `wss://`.

Графіки показують заряд і потужність батареї, мережі та резервного виходу. За замовчуванням вибрано «Сьогодні». «Сьогодні» й «Вчора» відповідають календарній добі за київським часом. У «Дати» можна вибрати діапазон включно з кінцевою датою. Щоб переглянути один день, вкажи однакові дати. Також доступні рухомі періоди за останню 1 годину, 6 годин і 7 днів.

За кожен проміжок показано останній збережений вимір. Для окремої доби проміжок становить 5 хвилин, для довших діапазонів його розмір зростає. Пропуски лишаються на графіку. Початкова історія, нові виміри та історія відключень надходять через той самий WebSocket.

На телефоні перемикай «Огляд», «Графік», «Архів» і «Виміри» кнопками або горизонтальним гортанням. Браузер запам’ятовує останній вибраний розділ і відновлює його після перезавантаження сторінки.

У розділі відключень можна вибрати чергу або всі черги. Браузер зберігає цей вибір у `localStorage` і застосовує його до графіка й архіву. Щоб переглянути попередні версії графіка, відкрий «Архів» на телефоні або знайди картку «Історія відключень» на широкому екрані та вибери дату. Час вимірів і графіків показано за Києвом.

## Telegram-сповіщення

Додай бота адміністратором Telegram-каналу з правом публікувати повідомлення. Задай змінні в `.env`. [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)

| Змінна | Значення |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен бота від BotFather |
| `TELEGRAM_CHAT_ID` | Ім’я публічного каналу на кшталт `@power_updates` або числовий ID каналу |
| `TELEGRAM_LOW_BATTERY_PCT` | Цілий поріг заряду від 1 до 100%, типово 20% |
| `TELEGRAM_DTEK_QUEUE` | Одна черга ДТЕК Київської області, наприклад `4.1`. Якщо порожньо, воркер надсилає лише сповіщення про акумулятор |

Воркер повідомляє про початок заряджання або розряджання, якщо в момент переходу заряд нижче 99%. Якщо розряд почався при 99–100%, воркер повідомляє, коли заряд уперше опускається нижче 99% під час розряду. Сповіщення про низький заряд надходить один раз при переході нижче налаштованого порога й може повторитися після відновлення заряду до порога. Перший відомий показник задає початковий стан. Після перезапуску воркер бере останні відомі показники з PostgreSQL.

Нові сповіщення використовують Telegram MarkdownV2. Воркер повідомляє про появу або зміну графіка тільки для вказаної черги. У повідомленні є час зі світлом і без світла за основним графіком на всю добу, з урахуванням півгодинних інтервалів. При оновленні воркер порівнює дві версії на ту саму дату й окремо показує зміни в планових і можливих інтервалах, навіть якщо загальний час зі світлом залишився тим самим. Для неповного або аварійного графіка воркер позначає тривалість як невідому. Порожній статус очікування й повторне отримання того самого графіка не створюють сповіщень.

У повідомленнях про акумулятор воркер додає стан за графіком цієї черги на момент виміру за київським часом. Він враховує півгодинні інтервали, можливі й аварійні відключення та позначає застарілий або недоступний графік.

Воркер зберігає чергу повідомлень у PostgreSQL і повторює доставку після збоїв Telegram. Застосуй міграції через `npm run bootstrap` і перезапусти `npm run worker`. У Compose виконай `docker compose up -d --build`. Без токена й каналу збір даних працює без Telegram.

## Homarr

У Homarr створи Custom API widget з HTTP source. Вкажи URL, доступний серверу Homarr, вибери **Basic** для Authentication і збережи логін та пароль з `.env`. За замовчуванням API опубліковано лише на `127.0.0.1` хоста. Локально запит можна перевірити через `curl`, який запитає пароль інтерактивно.

```sh
curl --user homarr 'http://127.0.0.1:3000/api/v1/stations/marstek-home/latest'
```

[Документація Homarr](https://homarr.dev/docs/management/custom-widgets/)

## Контракт API

`GET /api/v1/stations/{stationId}/latest` повертає JSON з `Cache-Control: no-store`.

```json
{
  "station": { "id": "marstek-home", "name": "Marstek Home", "model": "VNSE3-0" },
  "measurement": {
    "measuredAt": "2026-01-01T00:00:00.000Z",
    "socPct": 72,
    "remainingEnergyWh": 3660,
    "batteryPowerW": -510,
    "gridPowerW": 468,
    "acOutputPowerW": 468,
    "backupLoadPowerW": 0,
    "inverterState": 3,
    "workMode": 1,
    "upsEnabled": true,
    "dailyEnergyInWh": 120,
    "dailyEnergyOutWh": 200,
    "monthlyEnergyInWh": 8123,
    "monthlyEnergyOutWh": 3210,
    "totalEnergyInWh": 650000,
    "totalEnergyOutWh": 440000
  },
  "stale": false
}
```

- `200` повертає останній успішний вимір. `measuredAt` — час отримання відповіді станції у UTC (ISO 8601). `stale` стає `true`, коли вік виміру досягає `STALE_AFTER_MS`. Для відомої станції без вимірів `measurement` і `stale` дорівнюють `null`.
- `401` означає відсутні або неправильні облікові дані. `404` означає невідомий ID. `503` означає, що API не може обробити запит через конфігурацію або недоступність PostgreSQL.
- `socPct` вимірюється у відсотках. `batteryPowerW` додатна під час заряду й від’ємна під час розряду. Для `acOutputPowerW` і `gridPowerW` додатне значення означає віддачу з відповідного виходу станції, від’ємне — споживання через нього. `backupLoadPowerW` показує навантаження резервного виходу.
- `remainingEnergyWh` та енергетичні лічильники нормалізуються у Wh. `In` означає енергію заряду, `Out` — енергію розряду. Для залишку та лічильників EMS 150 використовується масштаб 10 Wh на крок, для `monthlyEnergyInWh` — 1 Wh на крок. Недоступний показник має значення `null`. Дійсний нуль зберігається.
- `inverterState` і `workMode` — коди станції. Для інвертора відомі коди `0` сон, `1` очікування, `2` заряд, `3` розряд, `4` резерв, `5` оновлення, `6` байпас. Для режиму роботи `0` — самоспоживання, `1` — ручний режим або UPS.
- За `workMode: 1` воркер приблизно раз на 10 секунд зчитує десятий слот налаштувань командою BLE `0x0A`. `upsEnabled` дорівнює `true` для ввімкненого UPS і `false` для ручного режиму без UPS. `null` означає, що вимір старіший за цю можливість, слот не вдалося прочитати або `workMode` має інший код. [Формат налаштувань BLE](https://github.com/sphings79/marstek-ble-control/blob/master/src/lib/payloads/GetWorkModeSettingsPayload.ts)

Воркер зберігає один рядок на кожну успішну відповідь. За інтервалу 1 с це до 86 400 рядків на станцію за добу. Історія зберігається в PostgreSQL без автоматичного видалення.

## Графіки відключень

Збір запускається разом із `npm run worker` або сервісом `worker` у Compose після міграцій `bootstrap`. Реєстрація станції для збору графіків необов’язкова. Контейнер воркера потребує системного сокета D-Bus і доступу до `https://alerts.energy`. Воркер отримує короткочасний токен зі сторінки черги 4.1 на кожному опитуванні.

Обидва маршрути повертають JSON з `Cache-Control: no-store` і використовують той самий Basic Auth, що й API станцій.

```sh
curl --user homarr 'https://power.example.com/api/v1/outages?queue=4.1'
curl --user homarr 'https://power.example.com/api/v1/outages/history?date=2026-11-11&queue=4.1'
```

- `GET /api/v1/outages` повертає `area`, `operator` (об’єкт з `id` і `name`), `timeZone` (`Europe/Kyiv`), `schedules`, `lastSuccessfulPollAt` і `stale`. У `schedules` входять сьогоднішні й майбутні дати з останньої успішної відповіді джерела. До першого успіху список порожній, а `lastSuccessfulPollAt` і `stale` дорівнюють `null`. Через три хвилини без успішного опитування `stale` стає `true`.
- `GET /api/v1/outages/history` повертає `area`, `operator`, `timeZone`, запитану `date` та `versions` у порядку спостереження. `date` обов’язкова у форматі `YYYY-MM-DD`. Повторення того самого графіка згортаються. Послідовність A → B → A дає три версії.
- `queue` необов’язковий в обох маршрутах. Без нього API повертає всі черги ДТЕК Київської області. Порожній результат повертається з `200`, некоректні параметри з `400`, неправильні або відсутні облікові дані з `401`, недоступність PostgreSQL або некоректна конфігурація Basic Auth з `503`.

Запис у `schedules` або `versions` має такий вигляд.

```json
{
  "queue": "4.1",
  "date": "2026-11-11",
  "status": "WaitingForSchedule",
  "hours": [],
  "possible": [],
  "publishedSchedule": null,
  "observedAt": "2026-11-10T15:00:00.000Z"
}
```

`hours` і `possible` містять погодинні коди від 00:00 за київським часом. `0` означає без відключень, `1` — усю годину, `2` — перші 30 хвилин, `3` — другі 30 хвилин, `9` — аварійні обмеження. Порожній `hours` означає відсутність погодинного плану. Порожній `possible` означає відсутність додаткових можливих відключень у графіку. Статус зберігає різницю між `ScheduleApplies`, `WaitingForSchedule`, `NoShutdowns` і `EmergencyShutdowns`. За наявності `publishedSchedule` містить `date`, `status`, `hours` і `possible` попередньо опублікованого графіка. `observedAt` і `lastSuccessfulPollAt` передаються в UTC у форматі ISO 8601.

За збою джерела API зберігає останній успішний результат. Якщо черга чи дата зникла з коректної відповіді, запис залишається доступним в історії. [Документація джерела](https://alerts.energy/developers/api/operators/source-registry-areas-slug-shutdowns)

## Перевірка

Для локальних npm-команд потрібен Node.js 24.

```sh
npm ci
npm run lint
npm test
npm run build
```

`npm test` запускає тести декодера, обміну, Basic Auth і графіків відключень. Для тесту міграцій, блокувань, ізоляції вимірів двох станцій та історії графіків задай `TEST_DATABASE_URL` до тестового PostgreSQL. Тест створює тимчасову схему.

На Ubuntu звір заряд, напрямок потужності й енергетичні лічильники з показниками Marstek. За стабільного з’єднання перевір оновлення часу приблизно щосекунди. Після втрати BLE-зв’язку API має зберегти попереднє значення й позначити його застарілим, а після відновлення показати новий вимір.

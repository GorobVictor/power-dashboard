# Power Dashboard

Вебзастосунок для моніторингу енергетичних станцій Marstek. Застосунок періодично опитує станцію через Bluetooth Low Energy (BLE), зберігає показники в PostgreSQL і надає їх через вебінтерфейс та HTTP API для майбутньої інтеграції з Homarr.

## Стек і межі MVP

- Використовуй наявний Next.js App Router (`src/app`), TypeScript і Node.js на сервері, shadcn/ui та Tailwind CSS для інтерфейсу, PostgreSQL для зберігання. Працюй з `npm` і `package-lock.json`.
- База, збирач телеметрії та API мають підтримувати кілька станцій. У першій версії інтерфейс показує одну станцію, вибрану через конфігурацію за її внутрішнім ID. Покажи окремий стан, якщо станцію ще не налаштовано.
- Почни з моніторингу та команд протоколу для читання телеметрії. Зміна налаштувань, керування зарядом і оновлення прошивки поза межами MVP.

## Bluetooth і збір телеметрії

- Робоче припущення для MVP — опитування виконує фоновий процес Node.js на хості з BLE-адаптером у зоні дії станції. Збір має працювати, коли вкладку закрито, і незалежно від запитів до API. Перед вибором BLE-бібліотеки уточни модель і версію прошивки станції, ОС хоста та доступ процесу до адаптера.
- Використовуй приклад як довідник з протоколу, зокрема для GATT UUID, команд читання, формату пакетів і складання фрагментованих відповідей. Звіряй їх з реальною моделлю та прошивкою. У прикладі транспорт працює через Web Bluetooth у браузері. [Marstek BLE Control](https://github.com/sphings79/marstek-ble-control), [код протоколу й транспорту](https://github.com/sphings79/marstek-ble-control/tree/master/src/lib)
- Відокрем BLE-транспорт, розбір пакетів і запис телеметрії. Зроби інтервал опитування налаштовуваним, уникай паралельних циклів для однієї станції, обробляй тайм-аути й повторно підключайся з поступовим збільшенням затримки.
- Зберігай останні успішні показники після втрати зв’язку. Відображай час вимірювання й окремо позначай відсутність даних або застарілі показники. Для недоступного показника використовуй `null`, оскільки нуль може бути дійсним значенням.

## PostgreSQL

- Веди окремі записи станцій зі стабільним внутрішнім ID та окремими полями для ідентифікації пристрою через BLE. Кожен вимір належить одній станції через зовнішній ключ `station_id`.
- Додавай зміни схеми через міграції. Зберігай час вимірювання у `timestamptz` та індексуй виміри за станцією і часом для отримання останнього запису та історії.
- Нормалізуй підтримувані показники під час запису. Документуй одиниці (`%` для заряду, `W` для потужності, `Wh` для енергії) і напрямок, якому відповідає знак потужності.

## Вебінтерфейс і API

- На дашборді показуй назву станції, останні доступні показники (наприклад, заряд і потужність) та час їхнього оновлення. Передбач стани завантаження, відсутності даних і втрати зв’язку.
- Створи HTTP JSON API лише для читання через Route Handlers у `src/app/api`. Для MVP надай останній збережений вимір за ID станції. Початковий варіант маршруту — `GET /api/v1/stations/{stationId}/latest`.
- Документуй формат відповіді, одиниці, час вимірювання в ISO 8601, ознаку застарілих даних і поведінку для невідомої станції та станції без вимірів. URL застосунку має бути доступною з сервера Homarr. [Homarr Custom API](https://homarr.dev/docs/widgets/custom-api/)
- Тримай підключення до PostgreSQL і BLE на сервері. Зберігай секрети в серверних змінних середовища. Для нової конфігурації документуй назви змінних і додавай лише безпечні приклади значень.

## Перевірка змін

- Для змін у коді запускай `npm run lint` та `npm run build`. Збірка має працювати без підключеної станції.
- Перевіряй розбір BLE-пакетів на знеособлених прикладах, а запити до бази — на даних двох станцій, щоб виявити змішування вимірів. На реальному пристрої перевір зчитування, втрату зв’язку та відновлення опитування.
